Tensor layout on Snapdragon¶

Research notebook · Nabil Zouhari

Question: does changing storage order reduce the work a neural-network compiler generates, and does the benefit survive beyond a single convolution?

This notebook follows the weather study's sequence: a small example from the definitions, an independent correctness check, measured execution, and a model application. It reuses saved device results. Running it submits no AI Hub jobs. The experiment plan was committed before the new model runs.

1. One operation, two storage orders¶

N, C, H and W mean batch, channels, height and width. For one 2-channel, 2×3 image, NCHW stores each channel's six values together. NHWC puts the two channels of each pixel next to one another. The colors below identify channels; reading left to right gives physical memory order. The numbers and their logical pixel positions are unchanged.

toy = hello_layout()
display(Image(filename=str(plot_storage(FIGURES))))

A 1×1 convolution with weights [2, 1] computes output[h,w] = 2 × channel0[h,w] + channel1[h,w]. The top-left pixel therefore gives 2 × 0 + 10 = 10 in either representation. An explicit-loop implementation is the reference; PyTorch is checked against it. This is a correctness exercise, not a speed measurement.

Strides tell us how far to move in memory when an index increases by one. permute can change shape and strides while sharing storage. Materializing the new order with contiguous() copies values in this example. A compiler may fuse or eliminate such a conversion; the source expression alone cannot establish its runtime cost.

A kernel expects a particular arrangement of values. Copies or packing needed to meet that interface consume time and memory bandwidth without changing the mathematical operation. This is the mechanism the device experiment investigates.

PyTorch's channels_last retains the logical NCHW shape and changes strides. An NHWC interface changes the axis order too. These are related but distinct representations. PyTorch memory-format explanation.

Simply calling reshape would assign the existing values to the wrong axes. The deliberately incorrect path below demonstrates why output validation matters.

print('Wrong reshape output:', toy['wrong_reshape_output'])

Wrong reshape output: [[1.0, 7.0, 13.0], [31.0, 37.0, 43.0]]

The measured convolution uses batch 1, 32 input channels, 64 output channels, a 3×3 kernel and ReLU. Only the external layout changes. Logical inputs, weights, device type, QAIRT version and requested options match.

QNN is the Qualcomm inference runtime whose call we time. HTP diagnostics describe execution on the Hexagon NPU. Generated HTP operations are not the same as the layers written in the original network.

At 64×64, median latency falls from 207 to 142 µs (31.4%), while transpose instances fall from 18 to zero. At 32×32, the medians are 103.5 and 109 µs and the ranges overlap. Removing transposes did not guarantee a measurable speedup at every size.

The trace supports a change in layout handling, but it does not assign the whole 65 µs difference to transposes. Other generated operations change too:

These were separate sweeps with uncontrolled cloud allocation and clocks. Input and output reordering were outside timing. The result describes a pipeline that can supply and consume the chosen layout, not a complete phone application. The raw comparison retains all cases.

3. Verify the setting before interpreting the result¶

The first sweep supplied HTP flags only during DLC conversion. Their application when the device prepared the graph was unverified. The correction explicitly sets them on inference jobs; runtime logs and graph evidence record the audit. Qualcomm documents DLC preparation and the relevant options.

The following corrected experiment keeps the 16×16 convolution fixed. The left panel measures QNN-call latency; the right counts HTP nodes in the first repeat. O1 and O3 are preparation settings, not graph-size guarantees.

display(Image(filename=str(plot_preparation(ROOT, FIGURES))))

O1 produced 24 nodes instead of 47, yet median latency increased from 80 to 91 µs. Node count treats very different operations as equal, so it cannot stand in for runtime. The folding-disabled request produced 47 nodes and a timing range overlapping O3. These measurements do not establish a folding benefit.

This is the same kind of check used in the weather research: validate what the implementation actually does before interpreting an option or a default.

The numerical gate failed¶

The model test exposed a limit before it could support a speedup claim. The predeclared rule checks every logit against the CPU FP64 reference:

abs(output − reference) ≤ 0.01 + 0.01 × abs(reference).

Left: the largest error divided by its allowed error. A value above the dashed line at 1 fails. Right: how many of the 1,000 logits exceed their allowance. Orange shows the NPU's three-job median and range. Gray is an additional CPU FP16 calculation made after the rejection to investigate reduced-precision error. It is a diagnostic comparison, not a replacement acceptance rule.

The three NPU repeats return identical error statistics, so their whiskers collapse to points. The local CPU FP16 path also crosses the fixed tolerance. This shows that the threshold can reject ordinary reduced-precision execution of the complete network; it does not identify a Qualcomm-specific defect. CPU FP16 is not an emulator of the NPU's kernels or accumulation strategy.

Preserving the top prediction does not satisfy a rule about all logits, nor does it establish dataset-level accuracy. The original acceptance rule stays unchanged. These runs remain rejected, their raw timings remain available for audit, and no validated whole-model speedup is claimed. The earlier convolution results retain their separate, passing checks.

The application question therefore remains open under this numerical contract. A follow-up should choose a task-level accuracy requirement on a representative dataset before measuring again, and assess how FP16 error accumulates through the network. It should not choose a new threshold merely to accept these outputs.

5. What remains to test¶

  • Repeat the layout pairs on a controlled physical device and alternate their order.
  • Include actual host preprocessing and transfers on that same phone.
  • Use multiple images and evaluate dataset-level accuracy before deployment claims.
  • Investigate the 32×32 case through kernel choices and format conversion, without assuming transpose count alone predicts latency.

GPU timings use different execution boundaries and are kept in the separate comparison. No NPU energy measurement is available. This notebook's contribution is the checked connection between representation, generated execution and measured latency.

Reproduce¶

Install the project with pip install -e '.[notebook]', then run python scripts/build_layout_notebook.py --with-vision from the repository root.
